# 清爽收纳 · 设计说明（v0.1 需求与结构）

> 一句话定位：**本地运行、绝不乱删、可撤销**的文件整理助手，Windows 桌面，面向不懂技术的普通用户。

---

## 0. 技术路线澄清（重要）

原始需求里同时出现了「Tauri 2」和「Python + CustomTkinter」，这两者不能共存：

| 方案 | 界面 | 后端 | 是否需要学 Rust | 是否符合本需求 |
| --- | --- | --- | --- | --- |
| Tauri 2 | HTML/CSS/JS | Rust | 需要 | ❌ 与「Python + CustomTkinter」冲突 |
| **Python + CustomTkinter** | CustomTkinter | Python 标准库 | 不需要 | ✅ 完全符合 |

**结论**：第一版走 Python + CustomTkinter，用 PyInstaller 打成 Windows 单文件 exe，通过 GitHub Releases 分发。这条路对新手最友好，也不需要装 Node、Rust 工具链。

Tauri 不是被否掉，而是**留到以后**：如果哪天要出 macOS/Linux 版、或者界面要做得更花哨，可以再评估。第一版不为此付出成本。

---

## 1. 需求分析与范围边界

### 1.1 用户的真实诉求（按优先级）

1. **别弄坏我的文件** —— 不删、不覆盖、能撤销。这是第一需求，高于一切功能。
2. **看得懂** —— 中文、大按钮、每一步都告诉用户"接下来会发生什么"。
3. **能反悔** —— 事后一键撤销。

### 1.2 第一版做什么（Must have）

| # | 能力 | 可验收的判定标准 |
| --- | --- | --- |
| F1 | 选择文件夹 | 点击按钮弹出系统文件夹选择框；选完显示路径与文件总数 |
| F2 | 扫描文件 | 只读取、不修改；扫描结果按分类统计；空文件夹有明确提示 |
| F3 | 六类分类 | 图片 / 文档 / 视频 / 压缩包 / 安装程序 / 其他，扩展名映射可查表 |
| F4 | 生成方案并预览 | 点「整理」**不移动任何文件**，只列出"哪个文件 → 去哪个文件夹" |
| F5 | 二次确认后执行 | 弹确认框，用户点「确认」才真正移动；取消则一切不变 |
| F6 | 不删除任何文件 | 全流程没有 `os.remove` / `unlink` / `rmtree` |
| F7 | 重名不覆盖 | 目标已存在同名文件时，自动改名为 `文件名 (1).扩展名`，并在预览里标出 |
| F8 | 记录操作 | 每次成功移动写一条日志（时间、源路径、目标路径、结果） |
| F9 | 撤销 | 按日志**倒序**移回原位置；目标已占用则跳过并提示，不覆盖 |
| F10 | 友好报错 | 权限不足、路径不存在、磁盘已满等，转成中文提示，不弹 Python 报错栈 |

### 1.3 第一版不做什么（Out of Scope）

- 递归整理子文件夹（**只处理选定文件夹的第一层**，理由见 §4.1）
- 按修改时间 / 大小 / 关键字自动分类
- 定时整理、监控文件夹
- 数据库、云同步、AI 识别、服务器
- 深色模式、动画、多语言

### 分层铁律

> **`core/` 里绝不允许出现 `import tkinter` 或 `customtkinter`。**

这一条决定了三件事：逻辑可以用 `unittest` 直接测、界面换成 Web/Tauri 时逻辑能复用、新手调试时能先跑通命令行版本再套界面。

## 3. 模块职责与数据流

```
用户点「选择文件夹」
        ↓
   ui/main_window  →  core/scanner.scan(folder)  →  List[FileItem]
        ↓                                              ↓
   显示统计（各分类多少个）                     ui 渲染统计条
        ↓
用户点「整理」→ core/planner.build_plan(items) → List[PlanItem]（含冲突改名）
        ↓
   预览表格（源 → 目标），不碰磁盘
        ↓
用户点「确认执行」→ core/mover.execute(plan)
        ↓                    ├─ 写 operation_log.jsonl（先写意图）
   结果汇总                  ├─ shutil.move 逐个执行
        ↓                    └─ 失败则该条标红，继续下一条
用户点「撤销」→ core/undoer.undo_last()  → 倒序移回
```

### 核心数据结构（`core/models.py`）

```python
@dataclass
class FileItem:          # 扫描产物
    path: Path           # 绝对路径
    name: str
    ext: str             # 小写，含点，如 ".jpg"
    size: int            # 字节
    category: str        # 图片/文档/视频/压缩包/安装程序/其他
    mtime: float

@dataclass
class PlanItem:          # 方案中的一条
    src: Path
    dst: Path            # 已包含重名处理结果
    category: str
    renamed: bool        # 是否因重名改过名

@dataclass
class MoveRecord:        # 写进日志的一条
    ts: str              # ISO 时间
    src: str
    dst: str
    status: str          # done / failed
    batch_id: str        # 同一次整理的批次号，撤销按批次走
```

## 4. 三个关键设计决策（都是"低风险优先"）

### 4.1 第一版只扫描选定文件夹的第一层，不递归

**原因**：递归会把子文件夹里的东西也搬走，用户很容易"整理一次，整个目录结构全乱"。而且递归撤销的边界情况（子目录被改名、被移动）会显著增加出错概率。
**代价**：子文件夹需要用户手动再选一次。
**后续**：v1.1 加一个「包含子文件夹」勾选项，默认关闭；核心逻辑只需在 `scanner.scan` 加一个参数，不动其它模块。

### 4.2 重名一律自动加序号，绝不覆盖

`报告.pdf` 已存在 → 新文件存为 `报告 (1).pdf`，仍冲突则 `(2)`，上限 999。
**原因**：覆盖是不可逆的数据损失，改名最坏只是多一个文件，用户自己能看清。
预览阶段就把最终目标名算好并标黄，用户确认前就知道会发生改名。

### 4.3 先写日志、再动文件（预写日志）

每次执行前，先把 `batch_id` 和全部待移动条目写入 `operation_log.jsonl`（状态 `pending`），每成功一条改 `done`，失败改 `failed`。
**原因**：如果程序在移动途中崩溃或断电，日志里仍有"打算移动到哪"的记录，撤销功能不至于变成瞎子。
**代价**：日志会有少量冗余行；完全可以接受。

## 5. 文件与数据存放位置

| 内容 | 位置 | 说明 |
| --- | --- | --- |
| 操作记录（撤销用） | `%APPDATA%\清爽收纳\operation_log.jsonl` | 一行一条 JSON，只追加不修改历史 |
| 运行日志（排查用） | `%APPDATA%\清爽收纳\logs\app.log` | 按天切分，保留 7 天 |
| 用户设置 | 第一版不做 | 避免过早引入配置系统 |

> 为什么不放在程序目录：exe 可能装在 `Program Files`，普通用户没有写权限。

## 6. 异常与中文提示（`utils/errors.py` 维护映射表）

| 技术异常 | 给用户看的话 |
| --- | --- |
| `PermissionError` | 这个文件夹没有修改权限，请换一个文件夹，或用管理员身份重新打开。 |
| `FileNotFoundError` | 文件已经不在了，可能被其它程序移动或删除。 |
| `OSError: No space left` | 磁盘空间不足，请清理后再试。 |
| 目标路径过长 | 路径太长，Windows 无法处理，请把文件移到更浅的目录。 |
| 未知异常 | 出了点问题，已记录到日志。可以点「撤销」恢复，或把日志发给开发者。 |

**原则**：任何情况下都不把 Python traceback 直接甩给用户；traceback 只进日志。

| 步骤 | 内容 | 验收 |

| M1（第三步） | 最小可运行：窗口 + 选文件夹 + 扫描 + 显示文件数与分类统计 | 双击能打开，选一个文件夹能看到"共 N 个文件，图片 a、文档 b…" |
